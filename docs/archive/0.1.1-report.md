# LrcRed Lyrics — Lyrico 歌词插件 0.1.1 完整开发、安装与独立复检报告

**版本**：0.1.1（图标增强试用版；包含 v0.1.0 全部功能与 QA）

**开发依据**：Lyrico 官方插件协议与宿主代码、`music-tag-lyrics` v1.8.5 的 `lrc_red.py`/TTML 处理思路、lrc.red 官方 API 条款。  

## 1. 包内文件与安装方式

本交付压缩包仅包含两份文件（**只有内层插件 ZIP 可直接导入 Lyrico**）：

1. **`LrcRed-Lyrics-0.1.1-Lyrico-Plugin.zip`** — 可直接由 Lyrico 导入的插件 ZIP；其中 `manifest.json`、`source.js`、`icon.png` 均位于 ZIP 根目录。
2. **`LrcRed-Lyrics-0.1.1-Development-Installation-and-QA-Report.md`** — 本报告。

**注意：请先解压最外层交付包，然后在 Lyrico 中导入里面的“Plugin.zip”，不要直接导入最外层压缩包。**

在 Lyrico 中打开 **设置 → 搜索设置 → 插件管理 → ＋ → 本地导入**，选择内层插件 ZIP。安装后进入 **LrcRed Lyrics → 配置**：

- 填写 **联系邮箱 / Contact Email**。这是 lrc.red API 要求的客户端联系邮箱，并非账号密码；邮箱会随 `User-Agent` / `X-Client-ID` 发往 `lrc.red`，因此请使用愿意向该服务公开的邮箱。未填写或不合规时插件不发起网络请求。
- **歌词匹配模式**：默认“均衡”，兼顾命中率和身份一致性；“严格”要求本地与远端的有效时长证据，并执行更严格的逐字覆盖检查。
- **开启模糊搜索兜底**：默认开启。当 `/match.json` 没有合格结果时使用 `/search.json`。
- 确认该插件在 **歌词源** 分类中启用。**它不会出现在封面源或元数据源中**，这是预期行为。
- 在 Lyrico 的 **设置 → 歌词 → 歌词模式** 选择你希望保存的格式。例如选择 **增强型逐字歌词（ELRC）**；之后用单曲编辑页的“搜索歌词”功能选择本插件，预览后应用，最后点击右上角“✓”保存到音频文件。

## 2. 功能范围与运行原理

### 2.1 仅获取歌词

Manifest 只声明 `getLyrics`。不实现 `searchSongs` 或 `searchCovers`；不改变标题、艺人、封面、作曲、年份等非歌词标签。所有写入由 Lyrico 宿主负责。

插件读取宿主提供的标题、艺术家、专辑、年份、时长；**不能保证宿主提供 ISRC**。若有合法 ISRC，先精确检索；否则按现有 Skill 思路执行：

1. `/match.json?track=...&artist=...` 结构化匹配；若没有合格结果，回退到官方公开文档描述的 `/search.json?q=...`。
2. 对合格 ISRC 请求 `/s/{isrc}.song.json`；如果不包含 TTML，按预算尝试 `/s/{isrc}.json` + `/s/{isrc}.ttml`。
3. 重新验证远端标题、艺术家、Live/Remix/Remaster 等版本信息、时长、`byModel` 和 TTML 逐字结构；明确冲突时拒绝，而不是猜测或硬选错误版本。
4. 可返回最多两条合格歌词候选供用户选择。需要通过返回的 `tags.ti/ar/al/date` 供 Lyrico 判断；缺少全部可用年份与专辑证据时拒绝候选，绝不捏造。
5. 返回 `type: "rawTtml"`；对 lrc.red 特有的 `lrc:` 命名空间进行兼容规范化，保留歌词内容与逐字时间戳，不在插件中重复实现 ELRC 渲染器。

### 2.2 ELRC 由 Lyrico 生成

宿主 `LyricEncoder.encode()` 读取全局 `LyricRenderConfig.format`。当用户选择 ELRC 而插件仅有 `rawTtml` 时，`LyricsDocumentPipeline.processRawResult()` 选择 TTML 为源格式，以 `EnhancedLrcWriter` 为目标格式，输出 ELRC；普通 LRC、逐字 LRC、TTML 则选择对应 Writer。

源 TTML 必须包含真实词级时间戳，才有高质量逐字 ELRC。翻译和音译是否输出、原文与翻译行序、繁简转换取决于 Lyrico 设置。演唱者、Ruby、段落等 TTML 特有结构无法完整保留在 ELRC 中。更改格式后应重新搜索，已保存歌词不会自动更新。

### 2.3 安全与限制

- 所有请求只指向固定的 HTTPS `https://lrc.red` 及其已定义路径；ISRC 必须符合 12 位合法结构；标题、艺人和查询参数使用 `encodeURIComponent`。
- 联系邮箱校验与 CR/LF 阻断；不硬编码私人邮箱；不在日志记录邮箱、歌词正文或 Token。
- 源响应最大检查：JSON 1 MiB 字符、TTML 2 MiB 字符，另受 Lyrico 宿主 8 MiB 网络响应上限约束；超大内容直接拒绝。
- API 返回 429/503 时暂停后续请求，并通过宿主缓存设置短期冷却；支持数值型 `Retry-After`（最长 300 秒）；不会在错误状态下无限重试。单次调用最多六个网络请求，软预算约 11.7 秒，宿主会独立限制插件执行时间。
- 仅将通过基础 TTML 结构验证且不超过 256 KiB 的正向载荷缓存 12 小时；**不缓存负结果**。缓存结果再次针对当前本地歌曲重新核验，防止跨歌曲误匹配。
- 有效 TTML 逐字行覆盖率：均衡模式 ≥ 80%，严格模式 ≥ 95%；时间倒序、非 TTML、无逐字信息、明显预览截断和强制版本冲突会被拒绝。`byModel === true` 的数据被拒绝。
- 这是一份完全独立的插件：**不会修改 music-tag-lyrics 原有 Skill，也不会操作 GitHub**。

## 3. 溯源与署名

歌词由独立社区服务 **[lrc.red](https://lrc.red)** 提供，不代表 Apple Music 官方歌词。插件名称、设置说明、返回候选的 `tags.source` 及 `tags.url` 均提供 lrc.red 署名/原曲目回链。应遵守 [lrc.red API 使用条款](https://lrc.red/api)：使用可联系邮箱标识客户端，展示数据时明确署名并回链。Android 实际 UI 是否把自定义 `source/url` 标签呈现为可点击链接，需要在真机上进一步检查，必要时再增强署名展示。


## 3.1 v0.1.1 新增：插件图标与深浅色适配

本次根据用户提供的 `Apple Music_Icon_2020.zip` 官方图形素材增加 **`icon.png`**，没有修改原来的歌词搜索、匹配和 TTML 处理算法。原始素材来自：

`Apple Music_Icon_2020/AppleMusic_Icon_BlackandWhite/SVG/Large/Apple_Music_Icon_wht_lg_072420.svg`

图像处理为：SVG 矢量轮廓 → 472×472 光栅化 → 512×512 画布 → 黑色圆角外框、白色底图与黑色音符（单色黑白），透明角落，最终 PNG 512×512。黑色与白色区域均为**同一张图片的固定像素**。在两种 UI 主题里都可辨认；不是宣称宿主能切换动态素材。已检查 40px 小图标视觉效果。

**为什么不直接加入两张主题 SVG？** Lyrico 的 `manifest.json` 只有一个 `icon` 字段，目前安装器只接受 PNG/JPG/JPEG/WEBP；实际 `PluginIcon.kt` 直接通过 Coil 绘制文件并不会根据主题对插件图做颜色反转或切换。所以仅声明 `"icon": "icon.png"`，使用深浅色都可读的单文件图标是兼容做法。背景会随应用主题变化，但图标画面本身不动态变色。

**品牌/图标授权提示：** 图标基于用户提供的 Apple Music 官方 SVG，仅做黑白图形适配，用于区分自定义歌词源。Apple Music 图形可能受商标和著作权规则约束；此次试用包不表示 Apple 官方认可，也不保证拥有向公众再分发或将其用于独立品牌的许可。若未来公开上架、发布到公共插件目录或商业分发，建议审核 Apple 的品牌使用规范，必要时更换为原创的 `LrcRed Lyrics` 图标。
